# Runner de notation des langages compilés (#116)

TOUTE exécution de code étudiant passe par un **conteneur jetable** `moodit-runner-*` lancé par
`execution-service` (Piston a été retiré). Deux modes du superviseur : « evaluate » (notation des
compilés **Go, Rust, C, C++, C#, Java**, décrite ci-dessous) et « exec » (exécution générique :
programmes RPC à nonce des interprétés/SQL/vues, et bouton « Exécuter » de tous les langages —
tout y tourne sous l'UID étudiant, sorties à la Piston). Le harnais du prof y est un
**CORPS qui renvoie un booléen**, compilé dans un programme séparé sous un UID séparé (le
noteur) — c'est la SEULE forme notée, un harnais au format framework (JUnit, NUnit, `go test`,
`cargo test`) étant refusé avec un diagnostic — et la POO est du simple code de
test (`new Rectangle(3, 4).aire()`), sans génération de code côté prof.

## Architecture

```
execution-service (DockerEvaluator)
  └─ docker run moodit-runner-<lang>     réseau none, mémoire/PID/CPU bornés, no-new-privileges,
       │                                 TOUTES les capacités retirées sauf le minimum root
       └─ supervisor.py (root)           ← processus de CONFIANCE
            pour chaque cas (ordre mélangé, 2 canaris insérés) :
              1. compile (root)          le HARNAIS + le nonce dans un programme (le noteur),
                                         le CODE SOUMIS seul dans un autre (le serveur)
              2. verrouille les sources  chown root, chmod 700 → EACCES pour l'étudiant
              3. lance le COUPLE         serveur sous l'UID étudiant (tiré au sort par
                                         conteneur, 1300 dans l'image), noteur sous cet UID + 1,
                                         tubes croisés, le noteur mène
              4. verdict FAIL-CLOSED     le nonce du cas sur le stderr DU NOTEUR, rien d'autre
            → un JSON unique sur stdout (verdicts + événements d'infrastructure)
```

Les fichiers du job sont copiés dans le conteneur **créé mais non démarré** (API `copyArchive`,
compatible docker-outside-of-docker : aucun montage hôte), en mode `0600` root ; la sentinelle
`.ready` est le dernier élément de l'archive.

## Modèle de confiance — ce qui est garanti, ce qui ne l'est pas

**Un seul modèle** : le harnais du prof est un corps qui renvoie un booléen, compilé dans un
programme séparé sous un UID séparé, et le verdict est le nonce que ce programme — et lui seul —
peut émettre. Le format « vraie classe de test du framework » (JUnit, NUnit, go test, cargo test)
a existé dans une version intermédiaire de #116 : il compilait le harnais AVEC le code de
l'étudiant, donc le processus qui détenait le secret était celui que l'étudiant contrôle, et cinq
canaux de forge y ont été démontrés. Il est retiré, et un harnais qui en porte le marqueur est
refusé avec un diagnostic plutôt que noté par un chemin contournable.

| Propriété | Mécanisme | Limite assumée |
|---|---|---|
| **Verdict NON FALSIFIABLE — les six langages compilés** (harnais booléen) | Le harnais du prof est un corps qui renvoie vrai/faux. Il est compilé dans un **programme séparé** (le noteur), lancé sous un **UID séparé**, avec le nonce ; le code soumis est compilé **seul** dans un autre programme (le serveur), sous l'UID étudiant. Tubes croisés, le noteur mène. Il appelle des **bouchons typés** générés à partir des signatures réellement présentes dans le code soumis (`javap` en Java, lecture de la source ailleurs), et il est le seul à détenir le nonce, qu'il émet sur **son** stderr — un flux que le processus étudiant ne tient pas. Chaque appel porte un **identifiant imprévisible** (tiré de `SecureRandom` / `crypto.randomBytes` / `random_bytes` / `/dev/urandom`) : le stdout du code noté EST le canal de réponse, et sans cet identifiant il pouvait répondre avant la question. La **POO est proxifiée par poignée** : l'objet vit chez l'étudiant (ses champs privés restent privés), le noteur n'en manipule qu'un numéro ; constructeur et — en Go et Rust, où le langage n'en a pas — littéral à champs nommés, par capture de champs | la garantie ne vient pas d'une détection mais de l'architecture : le processus de l'étudiant ne contient ni le harnais, ni le nonce, ni le verdict. Elle suppose en revanche que la signature appelée par le harnais soit **marshalable** (entiers, flottants, booléens, chaînes) : hors de ces types, le bouchon n'est pas généré et le harnais ne compile pas — message au prof, jamais un faux verdict. Le **hardcoding** reste possible (voir plus bas) : c'est la limite de tout système de tests fixes |
| **POO proxifiée — ce que le prof peut écrire** (harnais booléen) | L'objet vit CHEZ l'étudiant et le noteur n'en manipule qu'une poignée, donc les champs privés le restent. Deux idiomes : **constructeur** (`new Rectangle(3, 4)`, `Rectangle::new`, `NewRectangle` — y compris rendant `*T`), et **littéral à champs nommés** en Go et Rust, où le langage n'a pas de constructeur, par capture de champs | En capture de champs, l'objet est **reconstruit à chaque appel** à partir des champs du littéral : un état porté d'un appel au suivant ne survivrait pas. En **Go**, c'est l'étudiant qui choisit son récepteur : une méthode à récepteur pointeur (`*T`) reste donc en capture de champs, et son bouchon **relit les champs** chez l'étudiant après l'appel pour les recopier dans l'objet du harnais — la modification n'est pas perdue. En **Rust**, une méthode `&mut self` écarte ce mode et le type passe par la poignée d'un constructeur (un harnais écrit pour `&self` ne compilerait de toute façon pas contre elle) ; un type sans constructeur ET à méthode `&mut self` n'est pas proxifié : le harnais qui l'appelle ne compile pas, et le prof le voit. Un type **sans champ** (`struct{}` en Go, `struct T;` ou `struct T {}` en Rust) se construit par son littéral, et une classe **C++ sans constructeur déclaré** (hors classe dérivée) par son constructeur par défaut, comme en Java et en C#. En C++, une classe **abstraite** ou **template** n'est pas proxifiée (elle ne s'instancie pas telle quelle) ; ses classes dérivées concrètes le sont |
| **Contrat du canal de réponse** | Le stdout du code noté EST le canal de réponse, et les deux processus le partagent. Toute réponse est donc **auto-cadrée** : un saut de ligne AVANT, un APRÈS, dans les neuf répartiteurs (six compilés, trois interprétés). Sans cela, une dernière écriture non terminée par un saut de ligne (`print(…, end="")`, `print!`, `System.out.print`) se collait au début de la ligne de réponse, qui n'était plus reconnue : le couple s'attendait et une réponse JUSTE était notée « Interrompu ». En face, le lecteur ignore tout ce qui ne porte pas l'identifiant imprévisible de SON appel. Un test parcourt les neuf répartiteurs depuis une liste unique : ajouter un langage sans tenir l'invariant fait échouer la CI | le code noté ne doit pas FERMER sa sortie standard : c'est le canal sur lequel son propre processus répond. S'il le fait, le cas échoue avec « processus etudiant termine » — net et immédiat, jamais un faux verdict, mais un échec. Fermer la sortie dans un `main` ne coûte rien : sur ce chemin, le `main` soumis n'est jamais appelé |
| **Coût du chemin booléen** | Un cas compile DEUX programmes (le noteur et le code soumis), et TROIS en Java, où le code soumis est d'abord compilé seul pour que ses signatures soient lues sur ses classes. Le mur du conteneur et le miroir de core en tiennent compte (`DockerEvaluator.compilesPerCase`), sans quoi un cas lancé juste avant l'échéance du budget pouvait être tué au mur — tous les verdicts du job perdus, 502, tentative supprimée (#216) | une question Java à plusieurs cas dont les compilations sont réellement lentes atteint le plafond du mur (15 min) : elle est alors notée PARTIELLEMENT, les cas restants portant « Non évalué » (`budget_depasse`). C'est le comportement dégradé assumé, préféré à la perte de tous les verdicts. En pratique les compilations prennent quelques secondes, très loin de leur plafond de 90 s |
| **Types échangeables** | entiers, flottants, booléens et chaînes, générés d'après les signatures réellement présentes dans le code soumis. Les chaînes voyagent en **hexadécimal** et les flottants en `%.17g` : le fil est à champs séparés, donc un séparateur dans la valeur — ou un arrondi d'affichage — faisait noter FAUSSE une réponse juste | hors de ces types, le bouchon n'est pas généré : le harnais ne compile pas. C'est un message au prof, jamais un faux verdict. **Types reconnus, par langage** (paramètres et retour) : C et C++ `int`, `long`, `double` (pas `bool`, `long long`, `char*` ni `std::string`) ; C# `int`, `long`, `double`, `bool`, `string` (et leurs noms longs `Int32`, `String`…) ; Java `int`, `long`, `double`, `boolean`, `String` ; Go `int`, `int64`, `float64`, `bool`, `string` ; Rust `i32`, `i64`, `f64`, `bool`, `String`. **Ce qui n'est pas proxifié**, dans tous les langages : une méthode `void` (le harnais n'a rien à comparer : exposer un accesseur) et, en Java comme en C#, une méthode HÉRITÉE (seules celles déclarées dans la classe le sont ; une redéfinition `override` l'est). Les bouchons ne reproduisent pas non plus la **hiérarchie** : `Forme f = new Carre(2);` ne compile pas dans le harnais (le bouchon `Carre` n'étend pas `Forme`), il faut écrire `Carre f = new Carre(2);` ; les deux cas donnent « Le harnais ne compile pas », jamais un faux verdict, et `deploy/check-compiled-harnesses.py` les classe BLOQUANT. Le harnais **C et C++** dispose de `<math.h>` (`fabs`, `sqrt`…), `<stdbool.h>`, `<stdlib.h>`, `<string.h>` et `<stdio.h>` : le prof ne peut pas ajouter d'`#include`. Ces outils restent ceux de la bibliothèque : une fonction soumise qui porte le **nom** d'une fonction ou d'une macro de ces en-têtes (`fabs`, `sqrt`, `isnan`, `abs`, `round`…) est **refusée** avec un message clair. Elle prendrait sinon leur place dans le harnais, et une `fabs` qui renvoie 0 ferait passer tout `fabs(f(x) - attendu) < 1e-9`. Une question C ou C++ ne demande donc pas d'écrire `abs` ou `round`, mais `valeur_absolue` ou `arrondi`. Même règle en Go pour les identifiants prédéclarés (`max`, `min`, `len`…). Une **surcharge** est résolue par signature complète, types des paramètres compris, en C, C++, Java et C# (`Rect()` et `Rect(int, int)`, `f(int)` et `f(double)` sont distinctes) ; Go et Rust n'ont pas de surcharge. En Java, les classes **anonymes et locales** du code soumis (`new Comparator<>() { … }`) ne sont pas proxifiées : le harnais ne peut pas les nommer. En C#, une question proxifie **une** classe : la classe que le harnais nomme reçoit les bouchons (méthodes statiques de tout le code soumis, constructeurs et méthodes d'instance de cette classe) ; un harnais qui mêle `Solution.F()` et `new Rect()` ne compile pas. **En Go uniquement**, un flottant NON FINI (`NaN`, `±Inf`) n'est pas transportable : le protocole y est du JSON, qui ne les représente pas, et le cas est refusé explicitement plutôt que de bloquer. Les cinq autres langages les transportent ; une question Go dont la réponse attendue est un non-fini doit donc être formulée autrement |
| **Noms choisis par l'étudiant** | Le code généré (serveur côté étudiant, runtime côté noteur) ne dépend d'aucun nom que le code soumis peut porter. **Rust** : serveur et runtime du noteur dans un module à part, le code soumis atteint par `crate::` seulement. **C et C++** : le serveur n'inclut **aucun en-tête** (les quelques fonctions de la libc sont liées sous un nom `moodit_` par étiquette d'assembleur), ses locales sont préfixées, les appels C++ sont qualifiés `::f`. **C#** : serveur et runtime dans leur espace de noms, `using` à l'intérieur ; `global::System` dans les bouchons. **Java** : aucun import à nom simple dans le noteur ; dans le serveur, les types de `java.lang` sont nommés en entier (`java.lang.String`) ; une classe d'aide au nom d'un type de `java.lang` (`class Long`) que le harnais n'emploie pas ne reçoit pas de bouchon dans le noteur. **Go** : locales du serveur préfixées. **Python, JavaScript, TypeScript** : intégrées et objets globaux pris à la source avant le code soumis, symboles résolus hors des locales de la boucle. Vérifié par un balayage en compilation réelle : chaque identifiant du code généré et des bibliothèques qu'il importe, essayé comme fonction, fonction d'aide, variable, type, méthode et champ soumis | Restent **refusés, avec un message qui nomme le nom** : un nom que le *harnais* emploie et qui masque un outil du langage (intégrée Python, global JavaScript, commande Bash, identifiant prédéclaré Go, fonction ou macro des en-têtes C/C++ du noteur, classe de `java.lang`) ; en Go, toute déclaration de paquet au nom d'un identifiant prédéclaré dont le serveur se sert (`string`, `int`, `nil`, `true`, `len`…) ; en C et C++, une définition de `printf`, `fflush`, `fgets`, `strtol`, `strtod`, `malloc`, `calloc`, `realloc`, `free`, `stdin` ou `stdout`, que l'éditeur de liens substituerait à ceux du serveur — contrôle fait sur le **binaire** compilé (`nm`, sortie lue en entier), donc sur ce que le compilateur a produit et non sur l'écriture, fonction versionnée par `.symver` comprise (seule une *donnée* `stdin`/`stdout` versionnée à la main lui échappe, et si `nm` échoue il n'y a pas de refus : c'est un diagnostic, pas une barrière) ; une méthode `Pile::free`, un `using std::free;` ou une surcharge C++ (`free(Noeud *)`) n'en sont pas, alors qu'une réponse qui fournit son propre allocateur (`malloc`/`free` de même signature) est refusée. Non couverts, car le code soumis ne compilerait pas non plus seul ou le nom n'a aucun sens : un type soumis nommé comme un type primitif (`struct bool` en Rust), une classe C# nommée `System`, une classe Java nommée `java`, un nom préfixé `moodit` |
| **Exceptions du code soumis** | Une exception, un `panic` ou un arrêt du code soumis pendant un appel est relayé au noteur comme un **refus d'appel**, sans son type | le harnais ne peut pas tester **le type** d'une exception. En **Java**, le bouchon lève une `RuntimeException` générique : `catch (IllegalArgumentException e) { return true; }` ne l'attrape pas (`catch (RuntimeException e)` oui). En **Go**, le bouchon fait un `panic` que le harnais peut `recover`, sans en connaître la valeur d'origine. En **C#, Rust, C et C++**, le noteur s'arrête à l'appel refusé (« appel refuse par le code soumis ») avant que le harnais ne réagisse : le cas échoue. Une question « doit lever X » écrite du temps de Piston rend donc 0 à tous ; la reformuler avec une valeur de retour (code d'erreur, booléen, `Option`…). Le prof le voit en rejouant « Tester » avec sa solution |
| **Harnais illisible par l'étudiant** | le harnais n'est PAS dans le processus de l'étudiant : il est compilé dans le noteur, sous un autre UID. Les sources sont en plus verrouillées `700` root après compilation (`EACCES`) | le nonce du verdict ne va dans AUCUNE source ni aucun artefact que le code soumis puisse ouvrir : il est passé au générateur du noteur, qui le compile dans son propre programme |
| **CVE des images elles-mêmes** | Les dix images sont scannées par Trivy (`security.yml`, job `trivy-runners`), résultats CRITICAL remontés dans Code scanning. Bases épinglées par digest, téléchargements vérifiés par SHA-256 | **NON bloquant pour ces images**, contrairement aux sept images de service : au crible CRITICAL corrigeables, sept d'entre elles sont à zéro, mais `go` en compte une quarantaine, `c` (gcc) 205 et `rust` 208 — toutes venant des images officielles de chaînes de compilation, qu'une PR ne peut pas corriger. Bloquer dessus arrêterait le dépôt sur de l'amont ; réduire ces chiffres (bases plus minces pour c/go/rust) se décide à froid. Le job ne tourne pas sur les PR : dix constructions d'images par proposition pour un résultat informatif |
| **Pas de fuite réseau** | `--network none` | — |
| **Notation bornée dans le temps** | budget GLOBAL transmis au superviseur (mur du conteneur moins une marge, plafonné à **15 min**) : au-delà il CLÔT et renvoie les verdicts obtenus, les cas restants comptant « non exécuté » (`budget_depasse`) — le conteneur n'est plus tué au mur, ce qui perdait tout le travail et supprimait la tentative | une question à beaucoup de cas dont les compilations sont réellement lentes peut donc être notée partiellement ; le budget par cas (90 s de compilation) est très pessimiste par rapport au réel (quelques secondes) |
| **Pas d'épuisement de ressources** | mémoire/PID/CPU du conteneur + écritures étudiantes **confinées aux tmpfs bornés** `/box`, `/tmp` et `/dev/shm`, comptés dans la mémoire et **dérivés de `SANDBOX_MEMORY_MB`** (60 % / 6 % / 2 %, planchers 256 / 32 / 16 Mo — `DockerSandbox.boxSizeMb/tmpSizeMb/shmSizeMb` ; en dur, ils pouvaient dépasser la mémoire allouée au conteneur) (répertoires monde-inscriptibles des images verrouillés → le disque de l'hôte est hors d'atteinte du code étudiant) + rlimits (fichiers, nproc, nofile sur le processus ÉTUDIANT ; fichiers et nofile sur le NOTEUR — `demote_student`/`demote_grader` ; l'UID étudiant est **tiré au sort par conteneur**, sans quoi RLIMIT_NPROC — compté par UID réel sur l'hôte — aurait été un budget COMMUN : un étudiant qui fork en boucle faisait échouer la notation d'un autre) + temps limite par cas (prof, max 60 s) + budget mural du conteneur | — |
| **Isolation entre cas** | dossier par cas, groupe de processus tué au timeout, et **balayage des survivants UID étudiant après CHAQUE phase** — compilation, inventaire, notation — et pas seulement entre deux cas (un `fork` + `setsid` échappe au kill de groupe ; balayer tôt libère aussi les tubes de sortie, qu'un descendant survivant tenait ouverts, ce qui coûtait sinon dix secondes d'attente par phase) | pendant UN cas, les processus étudiants du même cas partagent l'UID (ptrace entre eux possible selon le `ptrace_scope` de l'hôte) — sans portée inter-cas grâce au balayage |
| **Interprétés, SQL et vues — mode exec** (Python, JavaScript, TypeScript, PHP, Bash, SQL, JSON, HTML, JSX/TSX) | Noteur et code soumis dans **deux processus** (RPC, identifiant imprévisible par appel), nonce émis par le noteur seul. Le noteur **Python** est lancé en mode isolé (`python3 -I`) : son dossier, que le code soumis peut écrire, n'entre pas dans `sys.path`, donc un `import numpy` du harnais ne charge jamais un module déposé par le code soumis. Seuls les symboles soumis que le **harnais nomme** reçoivent un mandataire dans le noteur ; parmi eux, un nom qui **masque un outil du harnais** est refusé avec un message clair (une fonction d'aide `max` ou `test` que le harnais n'appelle pas n'est donc ni mandatée ni refusée — même règle pour les compilés : Java, Go, C et C++) : fonction intégrée de Python (`bool`, `abs`, `len`…), global de JavaScript (`Number`, `parseInt`…) ou variable du module (`require`…), commande de bash ou du `PATH` (`test`, `expr`, `grep`… — vérifié par `type -t` dans l'image). Le verdict Python appelle la vraie `bool`, et un mandataire Bash rend le **statut** de l'appel réel. SQL : chaque instruction de la réponse est enfermée dans sa vue — coupée sur `;` **et** sur les lignes `go` et `/`, que `sqlite3` traite comme un `;` ; `sqlite3 -safe` (ni `.shell`, ni `.read`, ni `ATTACH`, ni `readfile`) ; programme livré **par stdin** depuis un fichier root `0600`, illisible même par la table virtuelle `fsdir`, que `-safe` laisse passer | **garantie plus faible que celle des compilés** : il n'y a pas de second UID en mode exec, noteur et code soumis tournent sous le **même UID**. Un code soumis déterminé peut donc, selon la politique `ptrace` de l'hôte et ce que `/proc` expose d'un voisin du même UID, tenter de lire la mémoire du noteur. Ces langages conviennent aux exercices et aux quiz formatifs ; pour une évaluation à fort enjeu, préférer un des six langages compilés, seuls à porter la propriété « verdict non falsifiable ». Les falsifications corrigées pendant la revue de #246 (`bool` en Python, ligne `go` en SQL, `test` en Bash) ne demandaient **ni ptrace ni lecture de mémoire** : un nouveau répartiteur doit refuser tout nom qui masque un outil du harnais |
| **Socket Docker de l'hôte** | `execution-service` monte `/var/run/docker.sock` pour lancer les conteneurs runner | accès **root-équivalent à l'hôte**. `execution-service` est routé depuis Internet (`/exec/**` via le gateway) et analyse le code soumis, les harnais et la sortie des conteneurs : un défaut d'exécution de code dans ce service vaudrait l'hôte entier (Postgres et Caddy compris), là où l'ancien Piston restait confiné à son conteneur. Durcissement prévu : un proxy de socket restreint (cf. `deploy/DEPLOY.md`) |
| **Détection** | Il n'y en a plus, et c'est le propos : le harnais et le nonce n'entrent dans aucun processus ni fichier que le code soumis puisse atteindre, donc il n'y a rien à surveiller. Les événements restants portent sur l'INFRASTRUCTURE (`budget_depasse`, `espace_sature`, `erreur_superviseur`) et sur les canaris, qui vérifient que la chaîne tranche encore dans les deux sens | la capacité `SYS_PTRACE` n'est plus accordée au conteneur et `strace` a quitté les images : elles ne servaient qu'à détecter une lecture du harnais, nécessaire quand il vivait dans un fichier ouvrable. Le code soumis ne peut donc plus tracer le noteur, ni aucun processus d'un autre UID (entre processus étudiants d'un même cas, voir la ligne précédente) |

Le **hardcoding** (un étudiant qui code `if (x == 5) return 10;` pour les entrées visibles de
l'énoncé) n'est pas une falsification : c'est la limite de tout système de tests fixes — la parade
est pédagogique (varier les cas).

## Protocole

- `execution-service` construit l'arborescence (`HarnessProjects`) : `cases/<i>/src/…` par cas,
  `job.json` (`{language, timeout_ms, budget_ms,
  cases:[{index, name} | {index, canary:"pass"|"fail"}]}`).
  - `budget_ms` : temps total que le superviseur s'accorde pour l'ensemble des cas. Il le teste
    AVANT de démarrer un cas ; au-delà, les cas restants sont rendus « non exécuté ».
  - Un cas ne porte que son index et son nom. Les champs `harness_types`/`student_types`
    appartenaient au format framework : le code soumis y était compilé dans la même unité que
    le harnais, donc ses PROPRES tests unitaires étaient découverts et comptés dans son
    verdict, et il fallait les exclure. Les deux programmes séparés ont supprimé la cause, et
    ces champs avec elle.
- Les harnais canaris contiennent `__MOODIT_A__`/`__MOODIT_B__`, substitués par le superviseur
  avec des valeurs aléatoires AU RUNTIME (introuvables dans l'archive).
- Réponse (stdout) : `{"v":1, "results":[{index, name, passed, detail, ms}], "events":[…],
  "canaries":"ok|incoherents|indetermines|aucun"}`. Le côté Java (`DockerEvaluator`) est
  fail-closed : cas absent, JSON illisible ou erreur = jamais « réussi ».

## Dispositions par langage

| Langage | Image | Disposition | Verdict |
|---|---|---|---|
| Java | `moodit-runner-java` (temurin 25) | code soumis + `harnais_rpc.java` marqué | nonce sur le stderr du NOTEUR |
| C# | `moodit-runner-csharp` (mono) | `solution.cs` + `harnais_rpc.cs` marqué | nonce sur le stderr du NOTEUR |
| Go | `moodit-runner-go` | `main.go` + `harnais_rpc.go` marqué | nonce sur le stderr du NOTEUR |
| Rust | `moodit-runner-rust` | `solution.rs` + `harnais_rpc.rs` marqué | nonce sur le stderr du NOTEUR |
| C / C++ | `moodit-runner-c` (gcc 14, partagée) | `solution.c|cpp` + `harnais_rpc.c|cpp` marqué | nonce sur le stderr du NOTEUR |

Une seule disposition : le code soumis dans son fichier, le harnais du prof dans un autre, précédé
du marqueur `__MOODIT_HARNAIS__`. Le superviseur compile le second dans le **noteur** et le premier
dans le **serveur** — deux programmes, deux UID — et le noteur appelle des bouchons typés générés
d'après les signatures réellement présentes dans le code soumis.

  exécutable, boucle infinie, budgets, poids). En CI (`SANDBOX_REQUIRED=true`), une précondition
  manquante FAIT ÉCHOUER le job.
- Dev local : démon Docker requis (Windows : named pipe, détecté automatiquement par
  `DockerSandbox`). Sans démon ni images, les tests s'ignorent et l'évaluation compilée répond 502
  — côté core, la tentative en attente est alors SUPPRIMÉE (`quiz:attempt-failed`) et l'étudiant
  doit resoumettre : il n'existe pas de rejouage automatique.
